# The generator

`sync/` reads the pinned ontology and writes `protobuf/digitalbuildings/`.
Nothing else writes there, and it writes nowhere else -- `protobuf/extensions/`
is hand-written and `sync` never touches it (rule 16). This file is how the
generator is laid out and why; the rules it must satisfy are in `CLAUDE.md`.

Two commands, one model:

- `sync/cmd/sync` -- the schema. `just sync`. It emits 1,165 `.proto` files
  across 113 packages, and `just ci` is green on them: zero `buf lint`
  findings, zero api-linter findings, no config file, no suppressed rule.
- `sync/cmd/docs` -- the Markdown reference beside it. `just docs`. It emits
  113 `README.md` files, one per package, plus the index at
  `protobuf/digitalbuildings/README.md` and the specimen at
  `docs/sample-reference.md`.

**Each owns its own extension.** `sync` clears and writes `*.proto`; `docs`
clears and writes `README.md`; both prune directories left empty, which is how
a dropped package actually disappears. That split is not fastidiousness: the
emitter began with a single `RemoveAll` of the whole tree, which was correct
while `sync` was the only writer and silently wrong the moment `docs` existed
-- `just sync` deleted 113 files it had not written and could not replace. See
`sync/emit/tree.go`.

Both build the same `model.Model` and neither parses an emitted `.proto` back
in. A reference generated by re-reading the output would agree with the output
by construction and could not catch a generator that emitted the wrong thing.

## Laid out by stage

One package per stage, and a stage may only import stages above it. The order
is the dataflow, and a package that needs something from below it is a package
in the wrong place.

| Stage | Package | Does |
| --- | --- | --- |
| 1 | `sync/spec` | reads `sync/spec.yaml`, checks the pin against the checkout |
| 2 | `sync/load` | walks `ontology/yaml/resources/`, one reader per facet |
| 3 | `sync/ontology` | the ontology's own types: subfields, fields, states, units, connections, entity types |
| 4 | `sync/naming` | ontology identifier to proto identifier: abbreviations, plurals, casing |
| 5 | `sync/catalog` | the rename tables and accepted traps of rule 2 |
| 6 | `sync/model` | inheritance resolution, the general-type partition, resources |
| 7 | `sync/describe` | composes every comment from the ontology's own prose |
| 8 | `sync/ordinals` | the append-only field-number ledger |
| 9 | `sync/emit` | writes `.proto` text: files, messages, enums, services |

A tenth stage, `sync/plan`, was in the original design to hold a per-file plan
between the model and the emitter. It is not there: the emitter turned out to
need nothing the model does not already carry, and an empty pass-through
package would be a stage in name only. `sync/internal/docs` is stage 9's
sibling: the Markdown target, built on the same model.

### A decision two stage-9 targets share belongs at stage 6

Anything both targets have to know is a **model** decision, not an emitter
detail. Three moved out of `sync/emit` when `docs` arrived, and each was a live
drift risk rather than a tidy-up:

| What | Now in | Was |
| --- | --- | --- |
| a field's proto type, and its `field_behavior` | `model.Field` | `emit/field.go`, `emit/message.go` |
| what a state set's enum and file are called | `model.StateEnumName`, `StateEnumFile` | `emit/field.go` |
| the service name and the six method routes | `model.Resource.Methods` | `emit/service.go` |

The third one proves the rule. The first Markdown reference rebuilt the HTTP
templates by hand and emitted `GET /v1/buildings/*/fanCoilUnits/*` for a method
actually routed at `GET /v1/{name=buildings/*/fanCoilUnits/*}`. The binding in
a path template is not decoration -- it is what tells the transcoder which
segment is the resource name -- and a reference that documents the wrong one is
worse than no reference. Both targets read `model.Resource.Methods` now, so
they cannot disagree.

### Stage 3 is where the ontology's shape lives

The input is seven facets in three shapes, and the parser handles each
separately rather than generically:

- `subfields/subfields.yaml` -- 391 subfields in 7 categories. The categories
  are ordered, and that order *is* the field grammar: `agg_desc`, `agg`,
  `descriptor`*, `component`, `meas_desc`, `measurement`, `point_type`.
- `fields/telemetry_fields.yaml`, `fields/metadata_fields.yaml` -- a literal
  is either bare, or carries a numeric range (`fixed_min`, `flexible_max`, and
  the two other combinations), or carries a list of states. Which of the three
  decides the proto type: 953 numeric, 602 multistate, 10 bare. 19 of the
  numeric ones name no measurement subfield and are integers, not quantities.
- `states/states.yaml`, `units/units.yaml`, `connections/connections.yaml` --
  flat maps.
- `<NAMESPACE>/entity_types/*.yaml` -- 2,637 types with `implements`,
  `uses`, `opt_uses`, `is_abstract`, `is_canonical`, `guid`, `description`.

Two YAML traps that a generic loader gets wrong, both real:

- `states.yaml` has unquoted `ON:` and `OFF:` keys. A **YAML 1.1** reader
  resolves those to the booleans `true` and `false`, and the ontology's two
  commonest states -- 111 fields' worth -- then arrive named `True` and
  `False` and compile into a perfectly valid, entirely wrong enum.

  `gopkg.in/yaml.v3` follows the YAML 1.2 core schema and tags them `!!str`,
  so it is safe; `yaml.v2` is not, and neither is a decode into
  `map[any]any`. The parser reads through `yaml.Node` and checks the tag, so
  the reliance is explicit rather than incidental, and
  `TestStatesAreNotBooleans` pins it. (This trap is real: it bit the Python
  analysis that sized this repository before the generator existed.)
- `units.yaml` mixes two value shapes under one key: a family maps unit names
  to `STANDARD` or to a `{multiplier, offset}` pair, but five keys
  (`diameter`, `length`, `level`, `linearacceleration`, `impulse`) are *alias*
  strings naming another family. A reader expecting a map gets a string.

### Stage 6 is where the design decision lives

Rule 7 says the general type is the resource. Stage 6 is what implements it,
and it is three passes:

1. **Resolve inheritance.** `implements` is a DAG across namespaces --
   `HVAC/FCU_DFSS_CSP_CHWDC` implements `FCU`, `DFSS`, `CSP`, `CHWDC`, and
   each of those implements more. A bare name resolves within its own
   namespace then falls back to global; a `/`-prefixed name is explicitly
   global; `NS/NAME` is explicit. The result is one flat field set per type.
2. **Partition by general type.** A canonical type's general type is its name
   up to the first `_`, cross-checked against the namespace's
   `GENERALTYPES.yaml`. 82 `(namespace, general type)` pairs carry at least
   one canonical variant.

   The prefix is a *convention*, not a rule the ontology enforces, and one
   type breaks it: `ELECTRICAL/SWITCHBOARD` is canonical and implements
   `PANEL`. Walking `implements` to a declared general type is the fallback,
   and it is not a guess -- it is the ontology stating the relationship
   outright, which is better evidence than the name. Ambiguity is still an
   error.

   Two other declaration sites had to be recognised. The global namespace
   keeps `PMP`, `SENSOR`, `TK`, `VLV` and `USER_INTERFACE` in `global.yaml`
   rather than a `GENERALTYPES.yaml`, mixed in with `EQUIPMENT` itself and
   four markers that are not equipment -- so the discriminator there is
   inheritance, not position. And a namespace with no `GENERALTYPES.yaml` at
   all (`FACILITIES`, `PHYSICAL_SECURITY`, ...) has entity types that *are*
   the resources.
3. **Union the fields.** The resource carries the union of its variants'
   resolved field sets, every one `optional`. `AirHandlingUnit` is 450 fields
   over 410 variants.

   That 450 is worth pausing on: the same union counted over *raw* field
   references is 813. The difference is rule 12 -- 122 of those literals are
   enumerated upstream, and `supply_air_temperature_sensor_1` and `_2` are one
   repeated field here, not two. A count taken before collapsing enumeration
   overstates every large message by roughly half.

A canonical type whose general-type prefix names nothing in `GENERALTYPES.yaml`
is an error, not a guess -- add it to `generalTypes` in `sync/model` and say
which general type it belongs to.

### Stage 8 is the only stage that reads its own output

`sync/ordinals` loads `sync/ordinals.yaml`, assigns a number to every field
the ledger has not seen, and writes it back. It never reassigns and never
reuses a number a field has vacated -- a removed field's number is moved to
`reserved`. Rule 9 says why: the ontology inserts fields alphabetically into
existing `uses` lists, so position is not a stable numbering.

## The line caps

Go at **200 lines**, hand-written Markdown at **250**, generated `.proto` at
**200**, and the exemption list checked in both directions. `just cap` enforces
all of it; the reasoning, the exemptions and why each one is exempt are in
`docs/line-caps.md`.

## Why there is a workspace

`go.work` names `./sync` and nothing else today. An earlier draft of this
section said it also names `./codec`; it does not, and `codec/` is not written
yet. When it is, it is a separate module rather than a package inside `sync`,
because it is a *consumer* artefact -- what a client imports to convert between
an ontology field name and a proto field -- and it must not drag the
generator's YAML and protobuf-reflection dependencies along with it.

The reason there is a workspace at all is the one that bites: `gen/` is
deliberately **not** a member. `buf generate` writes Go there for the build
check, and a build inside a non-member module fails while the workspace is
active. `just build-go` sets `GOWORK=off` for exactly this reason -- and that
recipe is not written yet either.

## Tests

`go test ./sync/...`, run by `just test` and by `just lint` before anything
else. What is worth testing here is not the emitter's text but the stages that
make decisions:

- `sync/ontology` -- the two YAML traps above, both as fixtures. A regression
  on either is silent in the output.
- `sync/model` -- inheritance resolution against hand-checked types, the
  general-type partition, and `CheckCatalogue`.
- `sync/naming` -- abbreviation expansion and plurals, table-driven.
- `sync/ordinals` -- that a reload assigns nothing new, and that a removed
  field's number goes to `reserved` rather than back into circulation.
- `sync/emit` -- golden files for one resource per shape: a large one
  (`AirHandlingUnit`), a small one, an ontology facet, and a namespace with no
  general types (`Building`).

`just survey` is the other half. It prints what was parsed -- counts per
facet, per namespace, per general type -- and every field name that trips a
known AIP rule. Run it after a spec bump before anything else; it is how the
catalogue in `docs/conventions.md` was built and how it should be rechecked.
